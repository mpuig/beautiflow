The design brief for this example.

Design a fictional multi-tenant hotel SaaS on AWS with control-plane, pooled-production, dedicated-enterprise and security accounts. Show staff federation, tenant discovery, pooled versus siloed data planes, scoped cross-account provisioning and central audit. Keep network, database replication and authorization details in the two companion views. Distinguish credential, request and provisioning arrows.

Architecture assumptions & omissions
  • Scope: deployment overview. Cell services and Aurora clusters are aggregates, not single-AZ instances. The companion views expand identity/isolation and one pooled cell’s availability/recovery design. They are authored views, not automatic projections.
  • Assumptions: tenant onboarding writes an authoritative tenant-to-cell directory; discovery returns an endpoint to the browser. Each cell independently verifies identity, tenant assignment and membership. Discovery is not a trusted authorization shortcut.
  • The enterprise account has separate credentials, application resources and database. Pooled isolation additionally needs transaction-local validated tenant context, a non-owner database role, forced row-level policies and tests for bypass paths.
  • Provisioning uses an allowlisted cross-account role and CloudFormation. Organization-trail coverage, central bucket policy, KMS permissions and retention must be configured; API audit capture is not application-log capture. No deployed configuration is supplied.
